# Testing & Quality

## Testing Strategy

The `.claude/skills` layer has **no automated tests of any kind**. The skill files are Markdown configuration consumed by Claude Code; they are not executable code and cannot be unit-tested with conventional frameworks. Quality assurance relies entirely on two mechanisms: (1) human review of skill file content and template accuracy via Git pull requests, and (2) the `/audit` skill itself, which provides a form of post-hoc completeness checking on generated documentation output — not on the skill definitions themselves.

## Test Types

- **Unit:** None. No unit test framework is present. There are no test files anywhere in `.claude/skills/`.
- **Integration:** None. There is no integration test harness for verifying that a skill invocation produces correctly structured output against a known input codebase.
- **E2E:** None defined. The closest analogue is a full `/analyse` run against a real codebase, but this is a manual process with no assertions or automated pass/fail evaluation.
- **Documentation audit (quasi-testing):** The `/audit` skill spawns `doc-auditor` to check completeness of generated documents against templates. This is the only automated quality check, and it operates on outputs not inputs.

## Coverage

| Area | Coverage Level | Notes |
|---|---|---|
| Skill file correctness (frontmatter, prompt structure) | None | No linter or validator; correctness verified only by human reading |
| Template section completeness | None | No test checks that all 10 templates contain all required sections |
| Agent behaviour against known inputs | None | No golden-file tests or regression fixtures |
| `gh` CLI integration | None | No mocked or recorded test of issue creation |
| Output document structure conformance | Low | `/audit` provides post-hoc completeness checking on generated output, but only after a full analysis run |
| `migration-advisor` financial calculations | None | Arithmetic is performed by the LLM; no deterministic test validates calculation correctness |
| Multi-argument parsing in `create-epics.md` | None | No test of how the agent splits the `$ARGUMENTS` string |

## Critical Test Scenarios

No automated test scenarios exist. The following are the highest-value scenarios that would need manual validation:

- Invoking `/analyse` against a known codebase and verifying all 10 documents are written with populated (non-stub) content.
- Invoking `/audit` and confirming it audits the correct version directory.
- Invoking `/create-epics` and confirming no duplicate epics are created on a second run.
- Invoking `/assess-migration` with a populated `context/migration-inputs.md` and verifying the score and financial case reference the correct input values.

## Manual Testing

All testing is manual. Areas requiring explicit manual validation:

- Correctness of dimension scores in `/assess-migration` output relative to the codebase being analysed.
- Accuracy of financial break-even calculations in `migration-advisor` output.
- Correctness of epic dependency ordering in `/create-epics` output.
- Verification that `/audit` targets the intended documentation version directory.
- Verification that documents generated by individual `/document-*` skills match the template structure.

## Gaps

- **No test infrastructure at all** — no `package.json`, no `pytest`, no `Makefile test` target, no CI workflow running tests.
- **No golden-file fixtures** — there is no reference output that can be diffed against a new run to detect regressions in agent behaviour.
- **No schema validator for templates** — a Markdown linter or custom validator checking that templates contain the required `##` sections would catch template regressions before they affect the auditor.
- **No `migration-inputs.md` validation** — a pre-flight check confirming all required fields are numeric (not "Unknown") before the advisor runs would surface configuration errors earlier.
- **No CI pipeline** — `.github/workflows/` does not exist in this repository; there is no automated check on pull requests.

## Release Validation

> ⚠️ Unclear: No formal release process is defined. Based on CLAUDE.md ("Always push changes to GitHub after completing analysis"), the implied release process is:

1. Make changes to skill files or templates.
2. Run a manual end-to-end test: invoke the changed skill against a known codebase and review the output.
3. Run `/audit` against the generated documentation to check completeness.
4. Commit and push to `main` on `chrisrooney-max/legacy-migration`.

No version tagging, changelog, or PR review requirement is specified in CLAUDE.md or any other file.
